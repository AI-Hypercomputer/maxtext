Main branch · run time per merged pull request
This chart shows how long CI took on every merged pull request on main, and which phase of the run — build, queue wait, setup, or a device's tests — took the time. Overlapping runs, in the hover card, counts how many other runs of this pipeline were in flight at the same moment as this one, whatever started them. More runs at once means more jobs competing for the same runners. Bars run from the oldest merged pull request on the left to the newest on the right. The pull request number under each bar opens that pull request on GitHub in a new tab; its merge date is under it. The chart below breaks the same runs down by worker suite. A mark above a bar repeats its state: ▲ means the run was slower than recent runs, ✕ means it failed, ↻ means a job passed only when re-run. Hover a mark for its numbers; zoom in and it grows into a two-line label.

Worker time per merged pull request
This chart shows where each merged pull request's CI time went, worker suite by worker suite: every worker's runner wait, setup and tests, stacked. A worker suite is one test flavor of the CI workflow, for example cpu-unit, together with all of its parallel Execute Tests jobs. Bars run from the oldest merged pull request on the left to the newest on the right. Every bar is one merged pull request. Every slice is one worker suite, in its device's color. Hover a slice to follow that suite across all pull requests. Click a bar to list every suite's time in that run. Pick one suite to see one bar per worker instead. The pull request number under each bar opens that pull request on GitHub in a new tab; its merge date is under it. The chart above splits the same runs by phase.
